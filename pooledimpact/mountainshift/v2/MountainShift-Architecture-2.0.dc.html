Part I — Philosophy & First Principles

Mountain Shift OS is not a metaphor for an operating system running inside a browser tab — it is treated, deliberately, as a real one. Every layer below is built to the standard a native OS would set for itself: a machine layer that boots through POST, a kernel that schedules real processes, a filesystem with real permissions, a windowing system with real focus and z-order, and applications that are indistinguishable, from the user's chair, from native software. The browser is the hardware substrate; nothing about the design treats it as a limitation to be worked around rather than a target to be built for properly.

The unifying idea across every layer is a single governing primitive: BaseClassX. Every stateful object in the system — a CPU register file, a file node, a kernel process table entry, a window, a translation AST node — is a BaseClassX instance. That gives the whole platform, for free, a small set of properties that would otherwise have to be reinvented per-subsystem: a schema-enforcing Proxy (no object accepts a property it didn't declare), a fingerprint (SHA-256 over structural state, so any two instances — or the same instance at two points in time — can be diffed with certainty), a history/trace log, and a version. This is why a manifest, a file node, and a translation tree can all be "diffed across environments" using the same verb: they are the same kind of thing underneath.

A second idea, layered on top of the first: presence in a manifest, not a hidden CSS state, is what gates a surface. A nav item, a process, an app tile — if it isn't present in the governing structure, it does not exist for that session, rather than existing-but-disabled. This shows up as the SurfaceManifest release-gating system (Part IX) but is really the same idea as the Kernel's process table (Part V): the source of truth is a declared, inspectable structure, not a scattered set of ad-hoc flags.

A third, more recent idea (not yet load-bearing in 2.0, but architecturally anticipated): the OS is host to more than deterministic computation. S-Matrix (Part VIII) runs a real local LLM inside the same process model as everything else — visible in ps, schedulable, ownable. The working theory behind that integration is that an OS which can observe its own inference — token by token, layer by layer — has a diagnostic capability no external harness does: it can watch a model's internal state drift and flag it, the same way top flags a runaway process. That theory (informally, "Spectral Shift") is out of scope for this document's engineering detail, but it explains why S-Matrix is wired into the Kernel as deeply as it is rather than sandboxed off as a special case.

Three distinct classes of manifold recur across this platform's underlying theory: Matrix (S-Matrix's MatMul-based transformer state), Biological (the human brain, the reference model the theory works from), and Geometric — a separate, first-principles line of work predating Transformer architectures, expressed most directly in GeoJS: a deterministic reasoning engine that treats reasoning as a C²-continuous path through semantic space, with memory held as a three-tier NURBS/B-Spline/Bézier manifold rather than trained weights — no LLM, no statistical guessing, fully auditable. BaseClassX is deliberately positioned to satisfy all three at once (Matrix via schema-tracked numeric state, Geometric via the same schema applied to curve/manifold parameters, and direct structural lookup for anything simpler than either), which is why the same base class underlies both S-Matrix and the Geometric-manifold apps described in Part XIV (Anchor App).

Part II — The Machine Layer

Below the Kernel sits a small set of classes that model a machine, in the literal sense: something with a CPU, memory, and a boot sequence. This layer exists so that everything above it — the Kernel's scheduler, the process table's CPU%/Mem% figures — is grounded in a real substrate rather than invented numbers.

CPU.js

The reference mechanical interpreter: a register/memory/interrupt model in the tradition of a simplified x86. It is intentionally not a BaseClassX subclass — it is a runtime engine, held by reference from the classes that wrap it, not schema-tracked state. This is a deliberate exception to the "everything is BaseClassX" rule: a CPU's register file changes on literally every clock tick, at a rate and in a manner schema validation and fingerprinting would only slow down. The lesson generalizes — hot, high-frequency runtime state lives outside the Proxy in a WeakMap-held handle; only the state worth tracking, diffing, and auditing goes through the schema. The same pattern appears in LoadingIcon.js's DOM refs and timers, and in AppClasses.js's appVersions map.

Environment.js

Reads host facts that BIOS itself has no way to know before it exists: navigator.hardwareConcurrency, navigator.deviceMemory, user agent, screen geometry. Exposed via a single detect() call. This is the layer that makes the Kernel's CPU%/Mem% figures real rather than fabricated — the workload-sampling calibration in Procd (Part V) is normalized against the actual core count and memory ceiling this class reports.

Physical.js

Wraps CPU.js as a WeakMap-held runtime handle behind schema-tracked capacity and energy figures. This is the seam between the "hot" CPU.js engine and the "tracked" BaseClassX world above it — Physical is the BaseClassX object; the actual interpreter lives behind it, invisible to the Proxy.

Memory.js

A schema-tracked region ledger — allocations, frees, ownership — sitting over a volatile WeakMap-held backing store. Kernel.fork()/kill() calls through to Memory.alloc()/free(), so a process's memory footprint in ps is a real ledger entry, not a random number.

Kernel.js (machine-level)

A schema-tracked process table plus a round-robin tick() — the machine-level counterpart to the OS-level Procd scheduler described in Part V. Provides Kernel.ps(), which Procd's job-control demos (top, ps, jobs) now read directly, rather than maintaining their own synthetic process list — one process table, one truth, read by every surface that displays it.

BIOS.js

boot() runs POST, reads Environment, scans a configurable bootDeviceOrder, and hands off to a Kernel instance. UEFI is the firmware default; a BIOS-legacy path exists but is not currently used. This is the literal entry point of the machine — everything the user sees, from the login screen down, happens after this call returns.

Part III — BaseClassX: The Governing Primitive

Every schema-tracked object in the system — from a CPU capacity figure to a translation AST node to a Finder file entry — is constructed the same way: declare a _schema.properties contract, call super(), and the base class wraps the instance in a Proxy that rejects any write to a property the schema didn't declare. This is not a style preference; it is the single bug class this document keeps returning to (Part XII), because it is the single bug class the whole system is designed to make impossible: a silent, un-validated property write.

Two, and only two, legitimate ways exist to give an instance a new property: add it to the schema (the declarative default), or assign it after super() has returned inside the constructor (for values that are genuinely computed from constructor arguments, not part of the durable contract). Any other path — assigning onto a live instance from outside, patching in a property after the fact — is rejected by the Proxy and throws. This has already caught real regressions during development (a wallpaper-gallery Kernel-integration attempt that tried to set cores directly on a machine node, and an early File/Folder implementation whose mode/uid/gid chmod/chown support silently no-opped because those fields were never added to schema).

Beyond the Proxy, every BaseClassX instance carries:

  • A fingerprint — a SHA-256 hash over structural state, letting two instances (or one instance across time) be compared for equality or drift without a hand-written diff function.
  • History/trace — a log of state transitions, so any instance's provenance can be replayed, not just inspected at a point in time.
  • Versioning — every instance carries its own schema version, so a manifest, a file, or a process table entry can be diffed not just against another instance of the same type, but against an older version of its own contract.

This is why SurfaceManifestX (Part IX) is "just" an XML/XSD/XSL bundle wrapped in a BaseClassX instance rather than a bespoke config-loading module: wrapping it gets fingerprinting, trace, and versioning for free, which is exactly what lets staging and production manifests be diffed for unexpected drift without writing a diff tool specific to manifests.

Part IV — The Filesystem Layer

FileFsX is the OS's filesystem abstraction, and it is deliberately pluggable at the storage layer via a Mount abstraction. Four backends currently exist behind one interface:

BackendSelectorDurability
File System Access (picker)backend:'picker' (default)Real disk, user-granted
OPFSbackend:'opfs'Origin-private, durable
IndexedDBbackend:'idb'Durable, current IDE root default
localStoragebackend:'localStorage'Durable, small-capacity

The IDE's root mount (/) currently defaults to {backend:'idb', key:'meshui-root'}, which is the first concrete step toward "dynamic-TTY-by-default" — a session's whole filesystem, and anything written into it, survives a reload rather than living purely in memory. FileFsX.create() correctly awaits the mount's initial load() before resolving, so callers never race the actual data load.

On top of storage, FileFsX carries real POSIX semantics: per-node mode/uid/gid, a mount table exposed to the Terminal's mnt command, and — because File/Folder are BaseClassX subclasses — schema-enforced property writes, which is why chmod/chown only became real once those fields were added to _schema.properties (see Part III).

An anticipated extension, not yet built: TzGz.js, a compression layer over FileFsX using a growable UInt8Array-backed store with atomic transactional writes — effectively a self-growing file. The working plan is for this to be the backing format for an eventual OS installer/ISO image: BIOS-level decompression at boot, offset/length random access so the whole image needn't load up front, and an interface deliberately modeled on the real ISO 9660 contract so the format stays close to an industry standard rather than inventing a bespoke one. TzGz.js itself is already written; what remains is wiring it in as the installer's backing store rather than building the compression layer.

Part V — The Kernel & Process Model

The OS-level Kernel (distinct from the machine-level Kernel.js in Part II, though built on the same process-table idea) is the thing that makes "everything is a real process" true above the machine layer. Procd (formerly TopMonitor.js, renamed to match Unix's procd/process-supervisor naming) is the scheduler: it runs a setInterval-driven tick, and — per the working definition settled on during development — a process is anything that computes within that tick, not merely a window or an app shell. This is why closing a window that leaves an inference session running was flagged as a leak (Part XII): the window is chrome, the tick-driven computation is the process, and the two must be torn down together.

Concretely, opening a window is a real fork(); closing one is a real kill()/exit(); both go through Memory.alloc()/free() so the resulting ps/top memory figures are ledger-backed, not synthetic. CPU% is computed from actual workload sampling — a calibrated "work unit" run against the JIT-warmed baseline, normalized against real navigator.hardwareConcurrency core counts — rather than a random walk, so idle processes correctly show 0% rather than a plausible-looking fake number.

Job control is real: jobs, fg <id>, bg <id>, kill <id> are Terminal built-ins wired directly to Procd's job-control API, and both ps and jobs force fg 0 as a usability default — foregrounding the shell so a command that follows isn't swallowed by a still-running foreground process like top. kill <pid> on an app process is the equivalent of a force-quit: it terminates the window and its child processes without graceful cleanup, by design (a last resort for runaway processes or severe leaks, not the recommended path).

Demo processes — demo lasagna, demo chart, and similar — are registered as real Kernel processes too, not a parallel fiction: they show up in ps/top with real CPU% while running, and demo lasagna --console renders identically whether the target is the browser devtools console or the Terminal's own output pane, using the same render→clear→render animation loop top already uses.

Part VI — The OS UI Layer

The OS UI layer (OS/src/DesktopShell.dc.html) is the shell that makes the Kernel and filesystem visible and operable. It closely follows the visual language of a familiar desktop OS — menu bar, dock, traffic-light window chrome — deliberately, because that vocabulary is what lets a user's existing intuition transfer instantly. Underneath the familiar surface, every interaction is backed by a real syscall-equivalent rather than a purely cosmetic state change.

Window manager

Real drag/resize/minimize/maximize with correct z-order; each window carries a 1px #777777 border. Windows open maximized by default. A focus model was added specifically to solve a real usability gap: clicking a window's body (not just its title bar) now grants focus, via a 20%-opacity click-catching shim over the unfocused window that disappears the instant focus returns — a visual cue, not just a functional one.

Menu bar and Dock

The menu bar sits at a fixed 35px and is app-aware — its content swaps to match the focused window's app identity. The Dock is user-repositionable (bottom, left, or right) and its owning layout dynamically reserves space for whichever edge it currently occupies, rather than assuming bottom-only. The Dock's own z-index is intentionally 0, so a maximized window can fill the full available area (minus a 5px margin) without the Dock stealing space or blocking clicks; each Dock icon carries a tooltip.

Login / lock screen

Real password auth: root's password is SHA-256-hashed at boot via Web Crypto (never stored or compared in plaintext), checked on explicit login <user> [password]; the initial boot session auto-authenticates as root without a prompt, matching a single-user auto-login machine. useradd lets root create additional users at runtime with their own uid/gid/home/password hash.

Wallpaper is modeled as two independent surfaces — Desktop and Lock Screen — each backed by a named Gallery (a simple list of image URLs) that cross-fades on an interval, prefetched on creation for fast, near-real-time-feeling cycling. Guests are restricted to the default gallery only; admin accounts can define and assign their own. Falling back correctly matters: logging out as one user must not leave the next session's lock screen showing the previous user's gallery — a guest logging out must see the default, never an admin's personal photos. The login screen itself fades to idle after 30 seconds of inactivity (mouse, click, or spacebar wakes it), which is deliberately the first building block toward an eventual kiosk mode.

Navigation surfaces

Cmd+` drives a Mac-style app switcher (chosen specifically because Ctrl+` collides with a reserved browser shortcut). Shift+Space opens an Omni Search overlay that resolves several distinct kinds of input through one box: app launch, arithmetic (1+1 → 2, with a copy-result affordance), symbolic algebra (solve x^2=9, x), GraphQL/SQL queries against the domain model, natural-language translation via the AST Translator (Part VIII), and free-form LLM prompts as the fallback path when nothing more specific matches.

Part VII — The Terminal & POSIX Surface

The Terminal app is a genuine POSIX-flavored shell over FileFsX, not a themed input box. On init it creates an in-memory Unix directory scaffold (/bin, /usr/bin, /etc, /home, /var, …). loadCommands() reads .js command files out of /bin and /usr/bin, evaluates each, and registers it by its static name field — dispatch resolves loaded commands ahead of any built-in, so the command surface is genuinely extensible rather than hardcoded.

Every command file follows one contract: static metadata plus execute(args, {stdout, stderr, cwd, vfs, session}). That single contract is why namespacing works cleanly — unix.ls.js, unix.cat.js, unix.grep.js and similar sit in a unix.* namespace as one family of POSIX binaries; an emerging llm.* namespace (llm.chat.js) is a distinct family of AI-oriented commands under the same loader; a third-party app that ships its own json command is scoped by its own prefix. /bin was never meant to hold only POSIX binaries — it is a general loadable-command directory, and the namespace prefix is what keeps unrelated command families from colliding as the catalog grows.

Session and permission state is real: whoami, id, who, w, last, chmod, chown all read/write actual per-node mode/uid/gid and a real session log that last replays. Job control (jobs/fg/bg/kill) is wired directly to Procd, described in Part V. Shell-level glob expansion happens before argv is built, matching real Unix behavior (globbing is a shell-level concern, not something each command reimplements). The help/man split is deliberate and load-bearing: help lists command names only; per-command documentation, usage, and flag descriptions live behind man <cmd>, resolved generically off each command's static metadata rather than a hardcoded naming convention — a distinction preserved carefully even as demo and diagnostic commands were added, specifically so the catalog can grow without help's output becoming unreadable.

Part VIII — The Application Layer

Every application is a Design Component window, launched from the Dock, tracked as a real Kernel process, and — where it has persistent state — backed by FileFsX or the Kernel's own schema-tracked structures rather than component-local state that vanishes on close.

VB6 IDE

The flagship development environment: Finder-style Navigator (project tree), a Code mode with a line-number gutter and Members panel, a Toolbox with pinnable library selection, multi-language compile targets (JS/PHP/Python), and FileFsX-backed save/load via a persisted IndexedDB file handle (no repeated OS file picker once granted). Static analysis runs through CodeUtils, surfaced in a results modal. The IDE's own Terminal (Part VII) is the reference implementation every other embedding of the Terminal is checked against for parity.

Org Reports (HOPE Shelters)

The nonprofit domain app: staff, shifts, payroll, budget, and grant reporting over a schema-bound domain model (Staff.js, Shift.js, PayrollRecord.js, Expense.js, BudgetCategory.js, Grant.js, OrgPosition.js, Organization.js). Reports currently support Quick Filter (per-column text filter, no saved-view complexity yet) and a single Group By. Payroll is the only report currently wired to PDF export via doc-page; extending that to every report, and stamping an export timestamp plus a user/org public key for data provenance, is tracked in Part XII.

S-Matrix

A real local-inference app: loads a quantized LLM via WebLLM/WebGPU, runs actual token generation, and — uniquely among apps — makes its own runtime state (the model's "S-Matrix," in the sense of Part I's Spectral Shift framing) inspectable the same way ps/top inspect a normal process: cache/IDB persistence, context size and window controls, named sessions (list/select/delete/replay/export/import), and "branching" — starting a new session from a base model or from a prior saved session, which itself represents an accumulated delta rather than a fresh baseline. It is fully Kernel-integrated: loading, downloading, and inferring are each real, visible processes, and closing the window now correctly tears down the underlying inference process rather than leaking it (a genuine bug caught and fixed during development — see Part XII).

AST Translator

An English⇄Bulgarian (and, architecturally, English⇄any language) translator built on a Universal Meaning Node — a language-agnostic AST with branches for speech act, tense/aspect, entity resolution, mood, and polarity, extensible to evidentiality, dual number, clitic order, gender, honorifics, classifiers, ergativity, topic, kinship, and inclusive/exclusive marking as each language's parser needs them. The goal is explicitly not per-language-pair mapping but one tree that grows optional branches. The UI surfaces this directly: every translated word carries a tooltip back to its source-language token and, in debug mode, to the AST node that produced it — so a translation can be audited word-by-word, not just accepted as a black box.

A complementary, geometric approach to the same problem exists as GeoNLP — GeoJS's natural-language extension (Part I): a 9-dimensional linguistic manifold (sentiment, formality, temporality, modality, agency, specificity, logical force, polarity, discourse), with polysemy, conditionals, and negation handled as branch topology rather than tree nodes (negation as geometric reflection, metaphor as cross-domain topological mapping, dialogue as dual-manifold branch resolution), and an IndexedDB-persisted GloVe/ConceptNet vocabulary manifold that survives across sessions without rebuilding. Symbolic AST and geometric manifold are two independent, no-LLM, fully auditable ways of modeling meaning — worth eventually cross-validating one against the other on the same sentence corpus rather than committing to only one.

App Store (Beta)

A curated storefront modeled deliberately on the mix of editorial content and mechanical install/uninstall that makes an app catalog feel alive rather than transactional: Discover (editorial feature cards and articles), Categories (browsable + ranked Top Free / Top Paid / Trending lists), an App detail page, and a Developer page. The core business mechanic is the free-app-as-doorway model: a public app (Guest-accessible) is free and complete on its own, while deeper OS-level capability behind it — extensions, subscriptions, additional paid apps — requires the full OS. Admins and developers get an editable view of their own App/Developer pages, gated behind a review step before changes publish. A Redeem (points-for-credit, airline-rewards-style) and Add Money to Account mechanic doubles as both a loyalty feature and a way to reduce per-transaction payment-processor fees by encouraging larger, less frequent top-ups.

Finder & the OS-wide file dialog

Finder is a first-class Dock app; the same underlying dialog also powers every other app's Open/Save surface, so improving it once improves every app at once. It understands FileFsX's multiple mounts as Locations (IDB, OPFS, etc., each addressable like a drive letter), supports Recents, honors the OS's dark theme, offers an expandable/collapsible browser panel (animated width transition, not an instant jump) for save flows that need format-specific extra options, and includes New Folder directly in the Save dialog's footer.

SlideDeck

A Keynote-modeled presentation editor, deliberately scoped to a small feature set done well rather than a maximal one: slide list, direct-manipulation canvas, Text/Image/Shape/Video/Audio primitives, a real SVG-native shape editor (draggable Bezier/B-spline control points, precise numeric x/y entry, duplicate/cut/copy/lock), a Properties panel following Apple's Style/Text/Arrange three-tab pattern, Custom Size (so the same tool doubles as a page-layout tool for print-style documents), and a command-line surface (SlideX new/import/save/export/load/macro/play) for scripted and macro-driven decks. Presenting a deck is a real Kernel process, matching every other app.

Network CRM & Finance Portal Pro

Two portfolio-company apps onboarded into the same Dock/window/Kernel model as the in-house apps, proving the platform boundary: an app doesn't need to originate inside MountainShiftOS to be a first-class OS citizen, it only needs to be a Design Component that plays by the same rules.

Part IX — Cross-Cutting Platform Services

SurfaceManifest-driven release gating

A platform-wide pattern, not an Org-Reports-specific feature: a nav/surface tree (left-nav, App Store category list, or any other tree-shaped surface) renders only the nodes present in an XML manifest. Absence — not a hidden or disabled state — is what keeps a surface out of a release, which makes the same primitive serve three purposes at once: light obfuscation-layer security (one layer among several; FieldACL and the BaseClassX proxy still own real field-level enforcement), config validation (an XSD contract per node — id, label, requiredRole, minAppVersion), and progressive-release/feature-flag gating. Each manifest is itself wrapped in a BaseClassX instance (Part III), so manifest drift between staging and production can be caught by fingerprint diff rather than manual review. HOPE Shelters' release ladder is the concrete first case — Tier 1 (PDF reports only) through Tier 5 (full internal), plus an independent Beta Partner tier — and the same shape is intended to gate every portfolio product (Deal Structure, Finance Portal Pro, GMAT, Learn, Together App) rather than being reinvented per app.

Filtering & Saved Views

Quick Filter (one text filter per non-money column, plus a single Group By) is the shipped default across Org Reports. Saved Views are explicitly deferred rather than half-built: the stated principle is that a saved view must never auto-repair or auto-migrate when the underlying schema changes — a view referencing a renamed or removed field must surface "this view needs to be updated or removed," never silently drop the reference or silently guess a replacement. A per-user/per-scope view limit (system-configurable, default 10) is planned alongside it.

UTF-24 / UTF-19 Timestamp Format

The OS's internal time representation, and a patent-pending solution to the Unix 2038 epoch overflow problem. UTF-19 is the dense, bit-packed 152-bit wire format (sentinel, 4-byte overflow/era extension, 8-byte signed seconds, 2-byte fractional component, 3 bytes of precision/offset/flag metadata, 1 reserved bit — no padding); UTF-24 is its in-memory counterpart, the same fields laid out as a byte-aligned 24-byte tuple so every field starts on a byte boundary, losslessly round-tripping to and from UTF-19 with no bit-packing overhead during normal use. A signed 64-bit seconds field plus a dedicated 4-byte overflow/era extension is what actually solves 2038 elegantly — Unix time's 32-bit second counter is the entire cause of that overflow, and this format simply never uses one.

The choice to keep epoch seconds (rather than move to a calendar-based representation) is deliberate: epoch time is efficient for AI and machine consumption — a flat, directly-comparable, directly-arithmetic integer — and UTF-24/19 preserves that property while fixing the one real defect (bounded overflow) instead of discarding the format's actual strength. This is intended as the OS's canonical internal timestamp wherever BaseClassX state, trace logs, or fingerprints need one.

i18n

Planned to ride the same schema-binding that already drives report fields — localized labels and number/date formats keyed off the same domain schema, rather than a parallel translation-string system, with the AST Translator (Part VIII) as the underlying engine for anything beyond static label lookup.

Debugging & Spectral Shift Theory

Spectral Shift Theory (Part I) is not purely philosophical background — it has a working, running test harness today: Anomalies_Test017, a 9-dimensional radical-movement detector built directly on the Geometric-manifold primitives (Part I, GeoJS). It places 72 points on a 9×8 torus (drawn from a Hebrew-name/gematria dataset used as synthetic test data), fits them with both a local B-spline and a genuinely delta-weighted global Bézier through the same control values, and computes an autonomy ratio — how sharply the local fit's derivative diverges from the global trend, normalized against that divergence itself — at any position t on the torus. A threshold (τ_q, the 99th percentile of the interior distribution) separates ordinary local variation from a genuine anomaly: a point where local behavior has meaningfully broken from the global shape. Three fixed "beacon" positions have their expected alpha values asserted against the live computation at init, rather than carried as unchecked hardcoded numbers — the harness checks its own math on every run.

This is the concrete debugging instrument Part I's Spectral Shift framing describes in the abstract: the same local-vs-global divergence math that flags an anomalous point on a synthetic 72-point torus is the working theory for flagging drift in a running LLM's internal state (S-Matrix, Part VIII) or in any other manifold-shaped process the OS hosts. Anchor App (Part XIV) is the planned home for this — a Torus-plus-Bézier Geometric Manifold app built directly on Anomalies_Test017's math, generalized from a fixed synthetic dataset to live, arbitrary manifold data.

Part X — Directory & Deployment Architecture

The canonical directory layout (documented, target-state as of this writing — the physical reorg is partially executed as parallel copies, not yet a cutover) organizes the whole portfolio as a holding structure:

PooledImpact/                      (holding company)
├─ Companies/
│  ├─ MountainShiftOS/             (the software company — only one with OS/)
│  │  ├─ OS/src/                   BaseClassX_x.x.xx.js (versioned) + alias
│  │  ├─ Apps/{IDE, Org}/          consume platform via unversioned alias
│  │  ├─ Website/, Docs/
│  ├─ CleanEnergy/                 (hardware — no OS/, runs on MountainShiftOS)
│  ├─ ConduitImpactCapital/        (fund — Apps/FinancePortalPro)
├─ Docs/                           cross-cutting (Spectral Shift, BaseClassX rubric)

Two conventions carry real engineering weight here. First, the platform-core alias: OS/src/ holds an immutable, versioned filename per release (e.g. BaseClassX_2.2.06.js) so any consumer that pinned to a specific version never breaks on upgrade, while an unversioned alias (BaseClassX.js, repointed on each release) is what in-house apps reference by default — current-by-default without a hand-bumped script tag. Second, every non-OS company's Apps/ folder is explicitly documented as running on MountainShiftOS's platform via that alias, never forking a local copy — the OS is infrastructure shared across the whole portfolio, not a per-app dependency.

Versioning follows a simple, git-bundle-compatible convention: the project archive is MESHUI_v{NNNN}.zip, incrementing on every bugfix, feature, or test pass; individual files inside an archive snapshot as {OriginalFileName}.xxx.html, where xxx is the version at which that file was last saved. The goal, stated plainly, is a running history compatible with an eventual Git or git-bundle migration — the archive convention is a bridge, not the final home.

Part XI — Security & Governance

Security in 2.0 is layered rather than singular: BaseClassX's schema Proxy enforces field-level shape at the object level; FileFsX's mode/uid/gid enforce POSIX-style permission at the filesystem level; SurfaceManifest gating enforces which surfaces exist at all for a given release tier or partner; and real SHA-256 password auth (never plaintext-compared) enforces identity at the session level. None of these is presented as sufficient alone — the manifest layer, in particular, is explicitly documented as "one layer among several," with FieldACL and the Proxy still doing the real enforcement work underneath it. Data provenance for exported artifacts (a user or organization public key embedded on every exported PDF, an export timestamp on every report) is planned but not yet universal — currently only the Payroll report carries export tooling at all.

Part XII — Known Gaps in 2.0

  • PDF export is wired to Payroll only; every other Org Report still lacks it, along with the universal export-timestamp and provenance-key stamp.
  • Saved Views are unbuilt; only Quick Filter + single Group By ship today.
  • The Staffing Coverage Report's gap-surfacing needs a dedicated fix pass — gaps are not currently shown clearly enough.
  • An Admin Schema Editor (editing _schema.properties/_fieldACL through UI rather than by hand-editing class files) does not exist yet.
  • Left Nav has no icons yet, and no configurable max-subsections-per-group cap.
  • Dedicated section landing pages (e.g., a Data Surfaces index listing all objects in a group with descriptions) are not built — navigation currently jumps straight to the first object in a group.
  • SurfaceManifest tiers 3–5 and the independent Beta Partner tier are undefined; only Tier 2 (Reports Only) exists concretely.

Part XIII.5 — Prior Art: The Pre-BaseClassX Kernel

Before the current BaseClassX-governed Kernel, roughly nine months of development went into a separate, non-schema-tracked kernel (~4,000 lines) with real depth: a platform-adapter layer abstracting browser/Node/service-worker globals behind one _platform object, a three-layer VFS with a sealed raw filesystem authority reachable only through a Symbol-keyed accessor, a token-based ServiceTokenManager (mint a token with pattern-matched operation:path permissions, expiry, and usage caps), a hierarchical ResourceManager enforcing parent/child process and memory limits, a real POSIX-flavored bsh shell (pipes, redirects, heredocs, quoting), an EtcResolver over passwd/shadow/sudoers, and session-stack su/sudo with token-based elevation.

Development on it stopped deliberately: none of that state was schema-tracked or fingerprintable, so every class managed its own state shape by convention rather than a shared, enforced contract — precisely the failure mode BaseClassX's Proxy exists to catch (Part III). Rather than retrofit governance onto four thousand ungoverned lines, the decision was to rebuild on BaseClassX from zero. The lesson is preserved rather than the code: several of that kernel's architectural decisions are worth carrying forward deliberately rather than being reinvented from scratch.

  • Platform adapter pattern — one object gating every browser/Node/service-worker global (crypto, fetch, WebSocket, indexedDB, spawn) rather than scattered typeof window checks throughout the codebase. Environment.js (Part II) already does the read-only half of this job (detecting host facts BIOS can't know before boot); it is the right home to grow the fuller adapter surface into as more subsystems need it.
  • Token-based permission model — the direction the current platform is headed for real security enforcement, not merely POSIX mode bits as decoration. The browser is the harshest security environment available (no real process boundary to lean on), so POSIX-style permissions can only ever be the familiar UX surface; a minted, pattern-matched, expiring token — ServiceTokenManager.mint(name, permissions, {expiry, maxUsage}) — is the actual gate underneath.
  • Session-stack su/sudo, not a stateless TTY — the old kernel's TTY started stateless, with "waiting for input" state living on a single shared TTY object; that produced a real queue-desync bug (two pending prompts could resolve out of order) once concurrent sessions existed. The fix — moving waiting-state onto a per-user Session object with its own queue — is the concrete lesson for the current Kernel/Terminal: any "awaiting input" state must live on the session, never on a shared singleton, or concurrent sessions bleed into each other.

Part XV — Theoretical Foundations: The Spectral Shift Stack

Beneath Part I's informal framing of Spectral Shift Theory sits a seven-document formal research stack, written substantially before the code that now implements pieces of it. This part distills each paper and, where one exists, names its concrete code counterpart — the point being that the running code (Anomalies_Test017, the Lasagna Demo, S-Matrix) is not decorative theming on top of the theory; it is a working, if partial, implementation of it.

Beacon Theory (BT-1)

A formal geometric framework: under a basis-dependent projection Π_B of a nonlinear system's state, a "beacon" is a persistent extremum of an induced autonomy field α(t), and Theorem 5.1 proves such non-monotone critical structure can only arise where the projection's induced metric g_Π becomes ill-conditioned (its inverse norm, or condition number κ, diverging) — a necessary but not sufficient condition. Beacon identity across perturbations is tracked via an optimal-transport distance over labeled extrema, giving permutation-invariant matching, and the time-indexed set of beacons forms a "Beacon Manifold." This is the proof behind Anomalies_Test017's autonomy-ratio formula (Part IX): the harness's alpha = |dD| / (|FB−D| + |D| + ε) is a discrete, single-dataset instance of exactly this local-vs-global divergence condition, and its τ_q threshold is a concrete stand-in for BT-1's instability-regime boundary.

Symmetric Subspace Construction (SSC)

Formalizes the geometry of permutation symmetry in high-dimensional representation: a fully symmetric state S = 1ₙ⊗s lies in an invariant subspace where the system's Jacobian rank collapses, trapping dynamics in a degenerate, repeated structure until a symmetry-breaking perturbation S_δ = S₀ + δP splits the collapsed eigenmodes and restores directional dynamics. This is the formal mechanism behind the Lasagna Demo (Part IX): a small model stuck repeating a token is, in SSC's terms, a system that has collapsed into its symmetric subspace and has not yet received a perturbation large enough to break out of it — the demo's S_delta = S_0 + delta*P, delta→0 output is SSC's own perturbation equation, run live.

Coupled Morse-Spectral System (CMS)

Couples an operator's spectral evolution to a Morse-theoretic topological observable derived from it via a smooth operator-to-scalar-field map: level sets of the induced field have a component count N(τ), a "bifurcation set" marks where that count changes, and Theorem 6.2 shows a sufficiently large spectral perturbation Δλ between successive states forces a bifurcation-set change — a topological transition. This is the general form of what Anomalies_Test017's single τ_q threshold-crossing implements as one concrete case.

Boundary-Constrained Representation Flow (BCRF)

Frames representation learning as a boundary-constrained continuous flow (segmented into discrete derivative steps at inference time) coupled to LLMG's discrete graph hops — flow segments become hops, gradients become edge weights, time becomes KV-cache indexing. BCRF explicitly names the SSC degenerate-symmetry regime the "Lasagna Limit" as its own defined case: rank collapse, repeated trajectory stacking, loss of directional differentiation — confirming the demo's name is a deliberate pointer into this formal stack, not merely a joke.

LLMG: Deterministic Graph Engine for Representation Inference

Proposes replacing stochastic token-by-token generation with deterministic graph traversal: each node is a representation-memory state (not a token), each inference step a weighted "hop" between nodes, the KV-cache reframed as a strictly time-ordered index rather than a recurrence buffer, and every transition recorded as a "pulse" (a state-shift vector) accumulating into a cumulative shift field Φ(t) — a trajectory memory of the system distinct from any single hop. AdapterHub/LoRA modules are first-class, hot-swappable graph operators (G_t → G_t^(A_i)) requiring no retraining to activate. This is the concrete engine behind the AdapterHub/LoRA backlog item (Part XIV) — not a vague plan, a designed deterministic alternative (or complement) to S-Matrix's matrix-multiply transformer.

LLMG Autonomy Transition Theorem

Gives a rigorous phase-transition condition for exactly the informal "AI drift/health" diagnostic sketched in Part I: the coupled spectral-representation/graph-inference system is autonomous — internally self-sustaining rather than externally driven — when the spectral radius of the graph transition operator ρ(J_G) exceeds that of the spectral-coupling forcing ρ(J_S·J_coupling). Below that threshold, perturbations propagate in from the spectral layer; above it, they're absorbed internally and inference converges to self-consistent graph equilibria (G* = 𝒯(G*)). This is the actual, falsifiable version of "an OS that can observe its own inference can diagnose it."

CAST (Cognitive AST)

The one document in this stack that is a direct engineering spec rather than pure theory: a content-addressable, provenance-mandatory, time-ordered cognitive graph (specified in SurrealQL) for persistent conversational memory — every fragment SHA-256-hashed for dedup and cross-reference, every edge carrying synaptic weight that strengthens with use and decays with disuse, every statement labeled with an epistemic status (fact/opinion/assumption/speculation/error/hearsay), and a defined protocol for federating queries out to external graphs. This is the literal mechanism for Part I's "content window is ephemeral, the OS is the manifold" claim: CAST is what would let an AI's understanding persist and accumulate across sessions rather than resetting with each context window, with S-Matrix's session/branch model (Part VIII) as its natural first consumer.

A live open insight: Beacons inside LLMG

LLMG's own appendix already states the flow–graph duality plainly (derivatives↔hops, gradients↔edge weights, time↔KV indexing) — meaning a hop chain is itself a discrete curve through representation space, the same shape as the Torus-plus-Bézier construction Anchor App and Anomalies_Test017 already use. The insight worth pursuing: embedding Beacon Theory's extrema-detection directly onto an LLMG hop-chain — rather than only on Anomalies_Test017's fixed synthetic torus — would let the same local-B-spline-vs-global-Bézier chain reaction that currently produces "learning" on the Torus run natively inside LLMG's actual inference graph, unifying Anchor App and LLMG into one mechanism instead of two parallel ones.

The performance case is as significant as the theoretical one. Because 𝒯(S_t, G_t) = arg max_{S'∈𝒩(S_t)} W(S_t, S') is a state-transition query over a bounded neighborhood — not a next-token probability distribution over an entire vocabulary — inference cost stops scaling with vocabulary size or autoregressive sequence length the way a transformer's does. A state-transition lookup is cheap, and because LLMG's async subsystems (KV indexing, hop exploration, pulse recording, shift aggregation, adapter activation) are only synchronized at evaluation/escalation gates (Part XV, LLMG paper §10), independent hop branches can be explored in parallel rather than serially decoded one token at a time. Both the Torus/Beacon math and LLMG's graph engine are, in this sense, cheap and parallel by construction rather than by optimization — a structural advantage over MatMul-based inference, not a tuning gain on top of it.
